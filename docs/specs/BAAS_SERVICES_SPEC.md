# Andy Code Cat — BaaS Services Layer: Specification

> **Status:** specification approved — deferred after R3/R5 (mature Layer 1)
> **Last architectural alignment:** 2026-07-15
> **Architectural dependencies:** double sandbox middleware (✅ implemented), Redis rate‑limiting (✅), nginx wildcard (R5)
> **Guiding principle:** static pages generated by Layer 1/2 acquire dynamic behaviours
> through calls to the Andy Code Cat BaaS — without the user writing any server-side code
> and without Andy Code Cat managing per-tenant runtime infrastructure.

> [!IMPORTANT]
> This is the broad capability catalog and contains historical SDK sketches. The current runtime,
> tenant-storage and security decision is
> [PLATFORM_CAPABILITY_RUNTIME.md](../architecture/PLATFORM_CAPABILITY_RUNTIME.md); the executable
> first slice is [FORM_RUNTIME_BAAS_IMPLEMENTATION_PLAN.md](FORM_RUNTIME_BAAS_IMPLEMENTATION_PLAN.md).
> In particular, generated artifacts no longer own `PF.*` submit/notification/webhook handlers:
> the LLM emits slots plus `serviceManifest`, and versioned platform runtime modules execute them.
> Direct anonymous Telegram/webhook triggers in this document are non-normative and must not be
> implemented.

## 1. Problem and solution

### 1.1 Gap between SOL‑1 and SOL‑3

Layer 1 produces high-quality static pages (SOL‑1). The next step in the original vision
(SOL‑3, full web app) requires per-tenant runtime infrastructure — effectively a mini-PaaS
built from scratch, expensive in ops and attack surface.

**The BaaS layer solves 90% of SOL‑3 use cases without any per-tenant runtime infrastructure:**

| What the user wants | SOL‑3 solution (discarded) | BaaS solution |
|---|---|---|
| Contact / sign-up form | Per-tenant Express endpoint | Declarative slot + `forms.capture` runtime |
| Product checkout | Per-tenant Node.js server with Stripe | Typed payment marker + platform adapter |
| Telegram order notification | Per-tenant Telegram bot | Internal event + queued Telegram adapter |
| CRM / email automations | Per-tenant custom logic | Internal event/outbox + verified connector |
| Editable product catalogue | Per-tenant database | Scoped `collections.records` capability |

### 1.2 The remaining 10%

Use cases not covered by the BaaS (real-time analytics dashboards, site-user authentication,
real-time chat, social features) fall outside the target use cases of Andy Code Cat (landing pages,
portfolios, basic e-commerce, professional sites). Users who need those are better served by
dedicated tools.

## 2. BaaS Layer Architecture

### 2.1 End-to-end flow

```
Published static page (e.g. https://myshop.Andy Code Cat.io)
         │
         │  declarative slots/markers from the LLM
         │  + version-pinned platform runtime files selected after generation
         │
         ▼
   Allowlisted capability runtime (vanilla JS, no artifact-owned secrets)
         │
         │  POST https://api.Andy Code Cat.io/v1/public/svc/{projectKey}/{service}/{action}
         │  Origin: https://myshop.Andy Code Cat.io  ← verificato CORS server-side
         │
         ▼
   Andy Code Cat API — BaaS Public Router (Express)
         │
         ├─ Resolve projectKey → active deployment + owner/project/capability
         ├─ Verify exact origin + enabled manifest/schema
         ├─ Validate DTO/purpose/retention + payload limits
         ├─ Rate limiting and idempotency on Redis
         ├─ Dispatch to application use case through domain ports
         │
         ├─ FormService    → capture scoped submission, emit typed event
         ├─ PaymentService → create Stripe Checkout Session, return redirect URL
         ├─ Automation outbox → email/Telegram/CRM/webhook adapters
         └─ CollectionService → policy-scoped structured records
```

### 2.2 Data entities

#### ProjectServiceConfig (embedded in Project)

```typescript
interface ProjectServiceConfig {
  // Public key embeddable in HTML — not a secret
  publicKey: string;           // UUID v4, generated on project creation
  // Authorised CORS origins — updated automatically on publish
  allowedOrigins: string[];    // e.g. ["https://abc123.Andy Code Cat.io", "https://www.example.com"]
  enabledServices: ServiceType[];  // ["forms", "payments", "telegram", "webhook", "catalog"]
  // Per-service configuration
  services: {
    forms?: FormsServiceConfig;
    payments?: PaymentServiceConfig;
    telegram?: TelegramServiceConfig;
    webhook?: WebhookServiceConfig;
    catalog?: CatalogServiceConfig;
  };
}

type ServiceType = 'forms' | 'payments' | 'telegram' | 'webhook' | 'catalog';
```

#### FormSubmission (collection: `form_submissions`)

```typescript
interface FormSubmission {
  _id: ObjectId;
  projectId: ObjectId;
  ownerUserId: ObjectId;      // tenant boundary

  deploymentId: ObjectId;
  formId: string;
  schemaVersion: string;
```

IP and user-agent are not stored in the submission. Short-lived abuse keys live in Redis; audit
can use a salted, non-reversible IP hash without payload values. All repository operations require
the compound `ownerUserId + projectId + capabilityInstanceId` scope. Physical collection strategy
and enterprise isolation tiers are normative in the Platform Capability Runtime decision.

## 3. Business model for services

### 3.1 Two operating modes for each service

Andy Code Cat supports two modes for each integrable service, selectable per project:

| Mode | Who owns the external account | Who pays external fees | Andy Code Cat earns | Setup required |
|---|---|---|---|---|
| **BYOK** — Bring Your Own Keys | The user/owner | The user | Monthly plan fee | Insert keys in the dashboard |
| **Managed** — Andy Code Cat key | Andy Code Cat | Andy Code Cat (passed on to user) | Transaction fee % | Simple onboarding only |

### 3.2 Per-service analysis

#### Payments (Stripe)

**BYOK:**

- The user has their own Stripe account (requires identity verification)
- Money goes directly to the user's Stripe account
- Andy Code Cat never touches the funds
- Suitable for: professionals, businesses, anyone doing significant volume
- Andy Code Cat fee: included in the monthly plan

**Managed (Stripe Connect):**

- Andy Code Cat has a Stripe Platform account
- Each Andy Code Cat owner who activates payments goes through a Stripe Express onboarding (5 min, simplified KYC)
- Stripe creates a Connected Account linked to the Andy Code Cat Platform account
- Payments go through the Platform account, with `transfer_data.destination` to the owner's Connected Account
- The owner receives funds to their bank account; Andy Code Cat retains the application fee
- **Suitable for:** hobbyists, small sellers, anyone who doesn't want to set up a standalone Stripe account

**Managed fee structure (example):**

```
€100 transaction:
  Stripe fee (EU cards): ~1.5% + €0.25 = €1.75
  Andy Code Cat platform fee: 1.5% = €1.50
  Owner receives: €96.75
  Total cost to the owner: 3.25% — competitive with PayPal (3.49%) and Shopify Payments (2%)
```

**IMPORTANT tax note:**
Andy Code Cat as a platform does not issue invoices for the owner's sales — Stripe handles
tax reporting directly. Andy Code Cat issues only its own service invoice for the platform fee.
The owner is responsible for their own accounting.

For small hobbyists and micro-businesses below VAT registration thresholds, the Managed Stripe
model is the path of least resistance: no business account needed, identity verified directly
through Stripe Express, personal bank account.

#### Telegram

**BYOK:**

- The user creates their own bot via @BotFather (1 minute, free)
- Inserts the token in the dashboard
- The bot is owned by the user; Andy Code Cat is only the relay
- Recommended: the user has more control, no dependency on the Andy Code Cat bot

**Managed:**

- Andy Code Cat has a shared relay bot
- The owner sends `/start` to the Andy Code Cat bot, obtaining their `chatId`
- All notifications go through the relay bot (e.g. `@Andy Code CatBot`)
- Downside: the bot can be pinged by anyone who knows the chatId (mitigated with OTP token for subscriptions)
- Recommended only as a simplified fallback for users unfamiliar with Telegram bots

**Recommendation:** BYOK Telegram is so simple that Managed adds no real value.
Offer Managed as the "simple default" with documented migration to BYOK.

#### n8n / Make / Webhook

Only BYOK makes sense: each user has their own n8n, Make, Zapier, or custom webhook instance.
Andy Code Cat only POSTs to the configured URL. No advantage to Managed.

#### Forms

Fully managed by Andy Code Cat (no external account required).
Submissions are stored in MongoDB in the project namespace.
Notification email via Andy Code Cat SMTP/Resend (included in the base plan).

## 4. Security — Configuration Guidelines

### 4.1 BaaS layer security principles

The BaaS is exposed to requests from anonymous visitors on the web — the attack surface
is different from that of Andy Code Cat's authenticated APIs.

**Fundamental rule:** no secret must ever leave the server. The client receives only
`projectPublicKey` (not a secret) and sanitised response data.

### 4.2 Configuration guidelines for user/project profile

#### Level 1 — Identity and access protection (MANDATORY)

| Control | Implementation | Notes |
|---|---|---|
| **CORS locked** | `allowedOrigins` verified for every public request | Updated automatically on publish. The owner can add custom domains. Wildcard `*` never allowed. |
| **Rate limiting per projectKey** | Redis sliding window: 60 req/min per `projectKey`, 10 req/min per `projectKey+ipHash` | Flood and submission-scraping prevention |
| **HTTPS only** | All SDK calls over HTTPS | The SDK rejects non-SSL calls in production |
| **IP hashing** | Salted SHA-256 of the IP for rate limiting | The real IP is never persisted in the DB |

#### Level 2 — Input validation (MANDATORY)

| Attack | Defence |
|---|---|
| **Form injection (stored XSS)** | HTML fields are rejected. Values are schema/type/length validated as plain strings, numbers or booleans and contextually encoded whenever rendered; the server does not turn arbitrary HTML into trusted content. |
| **Oversized payload** | 16 KB limit per submission. 50 items limit per checkout. 1000 char limit per form field. |
| **Field injection** | Only fields present in `FormsServiceConfig.forms[].allowedFields` are saved. Extra fields are silently ignored. |
| **SQL/NoSQL injection** | MongoDB: parameters passed as typed values, never interpolated into query strings. Mongoose schema validation before every write. |
| **Command injection** | Not applicable: the BaaS router does not execute user code. |

#### Level 3 — Secrets protection (MANDATORY for BYOK)

| Rule | Detail |
|---|---|
| **Stripe secret key never in MongoDB** | BYOK secret keys are encrypted with AES-256-GCM using an envelope key (env var `SECRET_VAULT_KEY`). Only the reference ID is saved in the DB. Plaintext is decrypted in memory only at point of use. |
| **Telegram bot token** | Same mechanism: envelope encryption, reference stored in DB. |
| **No secret logging** | The logging middleware explicitly excludes fields matching `*Key`, `*Token`, `*Secret` from logs. |
| **Secret rotation** | The owner can rotate their BYOK keys from the dashboard without downtime. The old reference is invalidated immediately. |
| **Principle of least privilege** | The service worker using the Stripe secret key has read access only to that specific record — not to the entire ProjectServiceConfig collection. |

#### Level 4 — Sandbox and isolation (MANDATORY)

| Rule | Detail |
|---|---|
| **Double sandbox on every write** | Even requests via `publicKey` are tracked with `projectId + ownerId`. No submission or order can be created without this pair. |
| **Cross-project isolation** | `publicKey` resolves to exactly one project. It is impossible to access another project's data via a different `publicKey`. |
| **Form submissions visible to owner only** | Submission read APIs (`GET /v1/projects/:id/services/forms/:formId/submissions`) are protected by `authMiddleware` + `projectSandboxMiddleware` — identical to other project APIs. |
| **Stripe webhook signature** | Every Stripe callback is verified with `stripe.webhooks.constructEvent()` + webhook secret. Unsigned requests are rejected with 400. |

#### Level 5 — Audit and monitoring

| Control | Implementation |
|---|---|
| **Execution logging** | Every BaaS layer call generates an event in `execution_logs` (TTL-90d collection — already implemented) with `domain: "baas"`, `eventType`, `projectId`, `ipHash` |
| **Anomaly detection (future)** | Abnormal submission rate for a project → owner email alert |
| **Abuse reporting** | Endpoint `POST /v1/public/report-abuse` for reporting misuse of an Andy Code Cat site |

## 5. API — Endpoints

### 5.1 Public BaaS API (no JWT — calls from anonymous visitors)

```
POST /v1/public/svc/:projectKey/forms/:formId/submit
POST /v1/public/svc/:projectKey/payments/checkout
GET  /v1/public/svc/:projectKey/catalog/list
GET  /v1/public/svc/:projectKey/catalog/item/:itemId
```

Telegram, email, CRM and webhook delivery are not generic public visitor actions. A validated
capability operation emits an internal typed event; server-side policy enqueues the configured
notification or connector through an outbox/job. This prevents a public project key from becoming
an abuse relay.

**Request/Response per forms:**

```typescript
// POST /v1/public/svc/:projectKey/forms/contact/submit
// Body (Content-Type: application/json, max 16KB):
{
  "name": "John Smith",
  "email": "john@example.com",
  "message": "Hello, I would like some information"
}

// Response 201:
{ "success": true, "submissionId": "uuid" }

// Response 429 (rate limit):
{ "error": "too_many_requests", "retryAfter": 3600 }

// Response 403 (unauthorised origin):
{ "error": "origin_not_allowed" }
```

**Request/Response per payments:**

```typescript
// POST /v1/public/svc/:projectKey/payments/checkout
{
  "items": [
    { "name": "Product A", "quantity": 2, "unitAmount": 2500 }  // in cents
  ],
  "customerEmail": "john@example.com",  // optional
  "metadata": { "sourceForm": "product-page" }  // max 5 kv pairs
}

// Response 201:
{
  "checkoutUrl": "https://checkout.stripe.com/pay/cs_...",
  "orderId": "uuid"
}
```

### 5.2 Owner API (JWT required — service management from the dashboard)

```
GET    /v1/projects/:id/services                  — project service configuration
PUT    /v1/projects/:id/services                  — update configuration
POST   /v1/projects/:id/services/payments/onboard — start Stripe Connect onboarding
GET    /v1/projects/:id/services/payments/status  — linked Stripe account status
POST   /v1/projects/:id/services/byok/stripe      — add/update Stripe BYOK keys
POST   /v1/projects/:id/services/byok/telegram    — add/update Telegram BYOK token

GET    /v1/projects/:id/services/forms/:formId/submissions   — list submissions
DELETE /v1/projects/:id/services/forms/:formId/submissions/:subId
GET    /v1/projects/:id/services/payments/orders             — list orders
GET    /v1/projects/:id/services/payments/orders/:orderId    — order detail

POST   /v1/stripe-webhooks                        — Stripe webhook (signature verified, no auth)
```

### 5.3 Platform runtime — public interface

Generated JavaScript does not call an open-ended BaaS SDK. The LLM emits declarative slots and a
typed `serviceManifest`; `prepareArtifactServices()` resolves the active project/deployment policy
and includes only allowlisted, version-pinned runtime modules.

Example form declaration owned by the LLM:

```html
<div data-pf-form-id="contact"></div>
```

The platform-owned form module renders controls, validates values and selects the configured
`mailto`, `relay` or `capture` adapter. Future catalog/payment actions require typed declarative
markers and capability-specific contracts; they are not arbitrary `fetch()` or `PF.*` calls
invented by the model.

## 6. Integration with the prompt system

### 6.1 Layer V + deterministic runtime

Capability protocol belongs to registered **Layer V**, not to an ad-hoc Layer A extension. Layer V
instructs the LLM to emit only approved declarative slots and a top-level `serviceManifest-v1`.
It prohibits custom handlers, endpoint invention, recipients, secrets, retention and legal claims.

The API persists the exact prompt trace and sends `layers[]` to Prompt Inspector. Layer V appears
even when empty and is non-empty only when a trusted preset/project configuration enables a known
capability. Runtime code is never prompt text: it is selected after generation from the platform
registry and shipped separately from `artifacts.js` with preview/publish/ZIP parity.

## 9. Architectural decision: BYOK first, Managed later

The recommended path is:

1. **BS1 (Forms)** — lowest external dependency and broad utility; still requires privacy/security review
2. **BS2 (Telegram BYOK)** — only requires the user to create a Telegram bot (1 min)
3. **BS3 (Payments BYOK)** — Stripe BYOK is usable by anyone with a registered business; requires no complex infra from Andy Code Cat
4. **BS4 (Payments Managed)** — requires: opening a Stripe Platform account, agreement with Stripe on marketplace terms, KYC compliance for Connected users → This is the step with the most legal and compliance work, not technical. It must be planned separately alongside the commercial/legal side.

> **BS4 is not just a technical milestone** — it requires Andy Code Cat to be registered as a Payment Facilitator or Marketplace under Stripe's terms. This has fiscal and liability implications. Validate with an advisor before implementing.
