# Form Runtime + BaaS Delivery — Agent-executable Implementation Plan

> Status: **proposal ready for planning; implementation not automatically authorized**
> Date: 2026-07-13; architectural alignment: 2026-07-15
> Parent spec: [BAAS_SERVICES_SPEC.md](BAAS_SERVICES_SPEC.md)
> Current decision: [PLATFORM_CAPABILITY_RUNTIME.md](../architecture/PLATFORM_CAPABILITY_RUNTIME.md)
> Roadmap constraint: R4 is suspended in [ROADMAP.md](../project/ROADMAP.md) until observability and publishing are stabilized.
> Operational goal: make the work executable in sequence even by an economy-tier model, with no implicit architectural decisions.

---

## 1. Expected Outcome

Andy Code Cat must offer a single declarative form module, reusable across preview, publish
and ZIP export. The LLM chooses the form's type and structure; the backend validates a manifest
JSON and a deterministic engine builds the behavior. Delivery is configurable without
regenerating the project:

1. `mailto` — initial default, no call to the Andy Code Cat backend and no submission
   persisted by the platform;
2. `relay` — validated public endpoint that sends via SMTP/API provider without saving the payload;
3. `capture` — public endpoint that saves the submission, exposes an inbox to the owner and can
   send notifications or double opt-in.

The system must prevent the LLM from inventing endpoints, recipients, credentials, legal bases,
retention or disallowed fields. The resolved configuration follows:

```text
PlatformFormPolicy
        ↓
User/Tenant EmailDeliveryProfile
        ↓
ProjectFormSettings
        ↓
ServiceManifest generated by the LLM
        ↓
ValidatedFormDefinition + public runtime
```

The `mailto` mode opens a draft in the user's client. It must not claim that the message was
sent. `relay` and `capture` are the reliable modes for production.

## 3. Verified Real Baseline

### 3.1 Already Implemented — Reuse, Do Not Duplicate

- `apps/api/src/domain/entities/ProjectPreset.ts` contains the `form` preset with wizard, validation,
  review and success state.
- `packages/contracts/src/vibecore.ts` exposes `interactive_form`.
- `docs/skills/template-skills/by-template/form/` contains the Layer S instructions for UX,
  validation, accessibility and product craft.
- `LlmStructuredResponse` contains `chat`, `artifacts`, `mediaManifest` and `focusPatch`.
- `chatRequestAdapter.ts` has the strict JSON schema used by providers that support
  structured output.
- `llmParser.ts` has a repair pipeline and the reusable precedent from the `mediaManifest`
  rescue for top-level, nested and double-encoded cases.
- `PreviewSnapshot`, `CreatePreviewSnapshot`, publish and export form the canonical path for
  artifacts.
- `CryptoService` uses AES-256-GCM and `MongoServiceApiKeyRepository` demonstrates the at-rest
  encryption pattern. It must be extended with domain separation, without changing the existing derivation.
- `authMiddleware` and `projectSandboxMiddleware` are mandatory for all owner APIs.
- `ExecutionLog` is the existing audit sink; do not create a second BaaS log collection.
- MongoDB and Redis are already in the Docker topology, but the API does not yet use a Redis client.

### 3.2 Not Implemented — Do Not Declare Done

- `serviceManifest` / `formManifest` in the LLM contract;
- manifest persistence in the snapshot;
- deterministic compiler/runtime for forms;
- `ProjectServiceConfig`, public project key and origin allowlist;
- SMTP profiles for platform/user;
- public Forms API;
- shared Redis rate limiting;
- submission inbox, retention and double opt-in;
- form/email profile settings UI;
- E2E tests for preview → publish/export → submit.

### 3.3 Conflicts Resolved by This Plan

1. The parent spec describes a `SECRET_VAULT_KEY`; the current code already has a `CryptoService`
   derived from mandatory secrets. This plan reuses `CryptoService` with an additive `context`
   parameter and an unchanged default. Do not introduce a second cipher.
2. The parent spec always saves `FormSubmission`; this plan separates `relay` from `capture` to
   allow sending without persistence.
3. The historical parent spec requires `PF.forms.submit()` calls generated in the artifact. This is
   superseded: the LLM emits slots + manifest; the platform-owned runtime chooses `mailto` locally
   or calls the public endpoint for `relay/capture`. `artifacts.js` does not implement the submit.
4. The vision talks about `serviceManifest`; do not create a competing `formManifest`. The
   canonical contract will be `serviceManifest`, initially with the sole `forms` capability.

## 4. Non-negotiable Invariants

### 4.1 Architecture

- Presentation routes call the use case; they do not access MongoDB directly.
- Application depends on domain ports, not on Mongo repositories or Nodemailer.
- Infra implements MongoDB, Redis, SMTP and encryption.
- The manifest validated in `packages/contracts` is the only shared contract.
- The runtime does not execute LLM-generated JavaScript to send data.
- The LLM neither receives nor emits credentials or SMTP configurations.
- `serviceManifest` is additive and versioned; output without a manifest keeps working.

### 4.2 Security

- Owner API: JWT subject + `x-project-id` + verification that `project.ownerUserId == jwt.sub`.
- Public API: project public key, origin allowlist, payload limit, schema whitelist, rate limit and
  redacted logging.
- No submission value in logs, errors, metrics or operational notifications.
- SMTP password encrypted at-rest and decrypted only in the adapter at send time.
- `from` comes from the verified profile; the visitor's email can only be `replyTo`.
- TLS mandatory: `implicit_tls` or `starttls_required`; no plaintext mode.
- BYOK SMTP host must pass an anti-SSRF and DNS-rebinding policy before connecting.
- HTML is not an allowed field type; user text is always treated as text.

### 4.3 Privacy

- The catalog can offer many fields, but the form uses the minimum necessary for the purpose.
- Special-category data under Art. 9 is forbidden by default.
- Acknowledgement of the notice and marketing consent are two distinct controls.
- `mailto` means "no Andy Code Cat persistence", not "no data processing".
- Productive newsletter signup requires proof of consent and double opt-in; `mailto` can only create a
  subscription request.
- Every `capture` submission carries `purposeKey`, notice version and retention expiry.

## 5. Canonical `serviceManifest` Contract

Create `packages/contracts/src/serviceManifest.ts` and re-export it from `index.ts`.

### 5.1 Shape v1

```ts
type FormKind =
    | "contact"
    | "commercial_lead"
    | "quote_request"
    | "booking_request"
    | "newsletter_request"
    | "feedback"
    | "survey"
    | "onboarding"
    | "custom";

type FormFieldType =
    | "text"
    | "email"
    | "tel"
    | "textarea"
    | "number"
    | "select"
    | "radio"
    | "checkbox"
    | "date"
    | "time"
    | "url"
    | "hidden_context";

interface ServiceManifestV1 {
    version: "service-manifest-v1";
    forms: FormDefinitionV1[];
}

interface FormDefinitionV1 {
    id: string;                    // kebab-case, max 48
    kind: FormKind;
    title: string;                 // max 120
    description?: string;          // max 500
    purposeKey: string;            // registry key, non-freeform after normalization
    steps: FormStepV1[];           // 1..5
    submitLabel: string;           // max 60
    successMessage: string;        // max 300; the mailto adapter normalizes it
    privacyNoticeRef: "project-default";
}

interface FormStepV1 {
    id: string;
    title: string;
    description?: string;
    fields: FormFieldV1[];         // 1..5 visible per step
}

interface FormFieldV1 {
    id: string;                    // field registry id, or custom-* allowed by policy
    type: FormFieldType;
    label: string;
    description?: string;
    placeholder?: string;
    required: boolean;
    autocomplete?: string;
    minLength?: number;
    maxLength?: number;
    min?: number;
    max?: number;
    patternKey?: "postal_code" | "vat_id" | "fiscal_code" | "custom_safe";
    options?: Array<{ value: string; label: string }>;
    dataCategory: "identity" | "contact" | "request" | "preference" | "consent" | "context";
}
```

### 5.2 Mandatory Zod Limits

- maximum 5 forms per manifest;
- maximum 5 steps per form;
- maximum 5 visible fields per step and 20 fields total;
- maximum 20 options per select/radio;
- lowercase kebab-case IDs, unique within their own scope;
- strings `.trim()`-ed with explicit limits;
- forbid unknown keys with `.strict()`;
- a consent `checkbox` cannot have a pre-selected value;
- `newsletter_request` must contain `email`, `privacy-acknowledgement` and
  `marketing-consent` as distinct fields;
- `hidden_context` can only contain allowlisted server/configuration values, never arbitrary
  query params copied without validation;
- `custom_safe` does not accept a regex emitted by the LLM: it resolves a regex configured by the system.

### 5.3 Maximal Standard Catalog

The catalog is a set of possibilities, not a list to be shown in full. Create
`apps/api/src/application/forms/standardFieldCatalog.ts` with at least:

- identity: `first-name`, `last-name`, `full-name`, `company`, `job-title`;
- contact: `email`, `phone`, `website`, `preferred-contact-channel`;
- request: `subject`, `message`, `service-interest`, `budget-range`, `timeline`;
- non-sensitive address: `city`, `province`, `country`, `postal-code`;
- appointment: `preferred-date`, `preferred-time`, `timezone`;
- feedback: `rating`, `feedback`, `would-recommend`;
- context: `project-name`, `source-page`, `campaign-code`;
- privacy: `privacy-acknowledgement`, `marketing-consent`.

Forbidden in the standard policy: health, biometrics, ethnic origin, religion, political opinions,
sexual orientation, judicial data, identity documents, passwords, credentials, payment cards and
file uploads. A future specialized capability will require another spec.

## 6. Configuration Separate From the LLM Manifest

### 6.1 `ProjectFormSettings`

Extend `Project` with an optional additive field:

```ts
interface ProjectServiceConfig {
    publicKey: string;
    allowedOrigins: string[];
    forms?: ProjectFormSettings;
}

interface ProjectFormSettings {
    enabled: boolean;
    mode: "mailto" | "relay" | "capture";
    recipientEmail?: string;          // fallback: account owner email
    emailDeliveryProfileId?: string;  // mandatory for relay/capture SMTP BYOK
    privacyNotice: {
        version: string;
        url: string;
        controllerName: string;
        contactEmail: string;
    };
    retentionDays: number;            // used only by capture; policy-clamped
    confirmationEnabled: boolean;
    doubleOptInEnabled: boolean;
}
```

Rules:

- `publicKey` is a random non-secret UUID, not a Mongo ObjectId;
- Mongo must have a sparse unique index on `serviceConfig.publicKey`; collisions generate a
  new key before commit, they do not overwrite the project;
- for legacy projects the key is created lazily on the first GET/PUT settings or via an
  idempotent migration; never regenerate it automatically;
- `allowedOrigins` does not allow `*`; the publish path updates the public origin automatically;
- `mailto` ignores `emailDeliveryProfileId`;
- `relay` does not use `retentionDays`;
- `capture` clamps retention to the platform policy;
- `newsletter_request` in `capture` requires `doubleOptInEnabled=true` before it can be
  considered a completed subscription.

### 6.2 `EmailDeliveryProfile`

New domain entity, kept separate from `ServiceApiKey` because it holds structured SMTP metadata:

```ts
interface EmailDeliveryProfile {
    id: string;
    ownerType: "platform" | "user";
    ownerUserId?: string;
    label: string;
    transport: "smtp";                // provider_api out of v1 scope
    host: string;
    port: 465 | 587;
    tlsMode: "implicit_tls" | "starttls_required";
    username: string;
    encryptedPassword: string;
    iv: string;
    authTag: string;
    fromAddress: string;
    fromName?: string;
    enabled: boolean;
    verificationStatus: "unverified" | "verified" | "failed";
    verifiedAt?: Date;
    createdAt: Date;
    updatedAt: Date;
}
```

Never return `encryptedPassword`, `iv` or `authTag` in DTOs. Return only
`passwordConfigured: boolean`.

### 6.3 Encryption Domain Separation

Modify `CryptoService` additively:

```ts
constructor(jwtAccessSecret: string, dbName: string, context = "service-api-keys")
```

Use `context` in the HKDF `info` parameter. The default must remain exactly
`service-api-keys`, so all existing keys remain decryptable. The SMTP repository uses
`email-delivery-profiles-v1`.

### 6.4 `PlatformConfig.formPolicy`

Extend the `PlatformConfig` singleton and the related admin contracts with an additive block. The
resolver must apply code-safe defaults even to legacy Mongo documents:

```ts
interface PlatformFormPolicy {
    enabled: boolean;
    allowedModes: Array<"mailto" | "relay" | "capture">;
    maxFormsPerManifest: number;       // default 5, hard max 10
    maxStepsPerForm: number;           // default/hard max 5
    maxFieldsPerForm: number;          // default 20, hard max 30
    maxVisibleFieldsPerStep: number;   // default/hard max 5
    maxPayloadBytes: number;           // default/hard max 16384
    maxTextFieldChars: number;         // default 1000, hard max 5000
    mailtoMaxUriChars: number;         // default 1800, fallback copy beyond threshold
    defaultRetentionDays: number;      // default 90
    maxRetentionDays: number;          // default 365, hard max 730
    allowUserSmtpProfiles: boolean;
    allowedSmtpPorts: Array<465 | 587>;
    requireTls: true;
    projectRequestsPerMinute: number;  // default 60
    formIpSubmissionsPerDay: number;   // default 10
    forbiddenDataCategories: string[]; // always includes the §5.3 categories
}
```

The "hard max" thresholds stay in code and cannot be raised by the admin. The UI can
reduce the operational limits, not disable TLS, the double sandbox, the sensitive-data block or
minimization. A project can only choose values stricter than the platform's. When it selects an
`emailDeliveryProfileId`, the resolver only accepts an enabled platform profile or a
profile with `ownerUserId == project.ownerUserId`.

## 7. Platform-owned Form Engine and Public Runtime

### 7.1 Rendering Ownership

The LLM emits only declarative slots in its own HTML:

```html
<section class="contact-flow">
  <div data-pf-form-id="commercial-contact"></div>
</section>
```

It can create CSS for the slot and for the documented public classes, but not the submit handler.
`FormRuntimeCompiler` verifies that every form manifest has a slot and that every slot points to an
existing form. Duplicate slots are allowed only if marked with unique `data-pf-form-instance`.

### 7.2 Deterministic Runtime

Create a vanilla JS runtime with no frontend dependencies, usable both inline in the ZIP and
as a versioned asset in publish:

```text
PF.forms.mountAll(runtimeConfig)
PF.forms.validate(formId, values)
PF.forms.submit(formId, values)
```

`PF.forms.*` is a namespace internal to the platform-owned module, not a contract the LLM must
invoke from `artifacts.js`. The compiler mounts the slots and wires the configured adapter after
generation.

The renderer must:

- generate associated labels, fieldset/legend for radios, errors with `aria-describedby`, progress
  state and a live region;
- use `textContent`/DOM API, never HTML concatenation with user data;
- preserve values across next/back;
- validate per step and on submit;
- prevent double submit;
- show loading, error, open-draft and success states;
- never show "sent" in `mailto` mode;
- be idempotent if run twice;
- support the absence of JavaScript with textual fallback and a contact address.

### 7.3 `mailto` Adapter

- build the URI only on click, never embed it with personal data in the page's HTTP URL;
- allow only `to`, `subject` and `body`;
- `to` and the subject template come from trusted configuration;
- strip CR/LF from headers and percent-encode UTF-8 per RFC 6068;
- short, textual body; no attachments;
- if the URI exceeds the configured operational limit, offer "Copy summary" and open a
  reduced draft;
- success state: "The draft has been opened. Review and send it from your email app.";
- show a fallback if no protocol handler is available;
- document that the recipient email is visible in the public artifact.

### 7.4 `relay/capture` Adapter

```text
POST /v1/public/svc/:projectKey/forms/:formId/submit
Content-Type: application/json
Origin: https://published.example
```

Canonical body:

```json
{
  "manifestVersion": "service-manifest-v1",
  "values": { "full-name": "...", "email": "...", "message": "..." },
  "consent": {
    "privacyNoticeVersion": "2026-07-13",
    "privacyAcknowledged": true,
    "marketingConsent": false
  },
  "context": { "sourcePage": "/contact" }
}
```

The server ignores extra fields and validates against the persisted manifest of the active
snapshot/deployment, not against a client-supplied whitelist.

## 8. Target API

### 8.1 Owner API — Always JWT + Project Sandbox

```text
GET  /v1/projects/:projectId/services/forms/settings
PUT  /v1/projects/:projectId/services/forms/settings
POST /v1/projects/:projectId/services/forms/rotate-public-key
GET  /v1/projects/:projectId/services/forms/:formId/submissions
GET  /v1/projects/:projectId/services/forms/:formId/submissions/:submissionId
DELETE /v1/projects/:projectId/services/forms/:formId/submissions/:submissionId
```

Public key rotation requires explicit confirmation and invalidates published artifacts that use the
previous key. Do not put it in the normal PUT settings.

### 8.2 Delivery Profiles

```text
GET    /v1/settings/email-delivery-profiles
POST   /v1/settings/email-delivery-profiles
PATCH  /v1/settings/email-delivery-profiles/:profileId
POST   /v1/settings/email-delivery-profiles/:profileId/verify
DELETE /v1/settings/email-delivery-profiles/:profileId
```

- a normal user sees only their own profiles;
- superadmin can manage platform profiles via an admin route or role-scoped in the same shell;
- a profile referenced by projects cannot be deleted without first disabling it and
  resolving the dependencies;
- `verify` runs an authenticated connection check without sending to arbitrary recipients.

### 8.3 Public API

```text
GET  /v1/public/svc/:projectKey/forms/runtime-config
POST /v1/public/svc/:projectKey/forms/:formId/submit
GET  /v1/public/svc/:projectKey/forms/:formId/double-opt-in/:token
```

The runtime config returns only public data: active manifest, mode, endpoint, privacy
text, mailto recipient if applicable, and UX limits. It does not return the internal profile ID,
SMTP username or secrets.

## 9. Persistence

### 9.1 Snapshot

Add `serviceManifest?: ServiceManifestV1` to `PreviewSnapshot`, the Mongo repository, DTO and use
case. The manifest belongs to the same version as `artifacts`; do not read it from the current
project when publishing a historical snapshot.

Saving happens on both the `chat-preview` and stream paths. Manual capture from a
message uses the parsed manifest, if present. The focused edit keeps the previous manifest
if the response does not contain a new one; if it does, it must be fully validated.

### 9.2 `email_delivery_profiles`

Indexes:

- `{ ownerType: 1, ownerUserId: 1, enabled: 1 }`;
- `{ ownerType: 1, ownerUserId: 1, label: 1 }` unique per scope;
- no index on ciphertext or username.

### 9.3 `form_submissions`

```ts
interface FormSubmission {
    id: string;
    projectId: string;
    ownerUserId: string;
    capabilityInstanceId: string;
    deploymentId?: string;
    snapshotId: string;
    formId: string;
    formKind: FormKind;
    schemaVersion: string;
    purposeKey: string;
    values: Record<string, string | number | boolean>;
    searchableFields: Record<string, string | number | boolean>;
    consentEvidence: {
        privacyNoticeVersion: string;
        privacyAcknowledgedAt: Date;
        marketingConsent?: boolean;
        marketingConsentAt?: Date;
        source: "web_form";
    };
    doubleOptIn?: {
        status: "pending" | "confirmed" | "expired";
        requestedAt: Date;
        confirmedAt?: Date;
    };
    status: "new" | "read" | "archived";
    submittedAt: Date;
    expiresAt: Date;
}
```

Indexes:

- `{ ownerUserId: 1, projectId: 1, capabilityInstanceId: 1, submittedAt: -1 }`;
- `{ ownerUserId: 1, projectId: 1, capabilityInstanceId: 1, status: 1, submittedAt: -1 }`;
- TTL `{ expiresAt: 1 }` with `expireAfterSeconds: 0`;
- double opt-in token saved only as a hash in a dedicated collection/token record or subdocument;
  never plaintext.

Do not save IP or user-agent in the submission. Abuse control uses TTL'd Redis; auditing uses a
salted, non-reversible IP hash without the payload.

`searchableFields` contains exclusively normalized copies of fields approved by the policy. Do not
enable arbitrary full-text search over PII values, and do not make encrypted fields searchable for
convenience. Owner list/detail/delete must receive a full scope
`{ ownerUserId, projectId, capabilityInstanceId }`; no tenant filter is optional.

### 9.4 Physical and Logical Isolation

Default: shared collections per capability (`form_submissions`, `capability_instances`,
`automation_jobs`) with mandatory composite scope on every document, index and query. Do not create
dynamic collections like `form:{tenantId}` and do not accept database/collection names from the
manifest or the client.

A dedicated database/cluster can be an enterprise tier for a few tenants with data residency,
backup/restore or dedicated scaling requirements. It must use the same domain ports and the same use cases: the
physical separation does not replace the double sandbox and query scope.

The public submit does not accept `ownerUserId`, `projectId` or `capabilityInstanceId` from the body. It resolves
`projectKey` against the active deployment and derives the server-side scope, manifest/schema, purpose and
retention before validating and persisting.

## 10. Standard GDPR Policy

Create a platform registry with known purposes:

```text
contact_request
commercial_lead
quote_request
booking_request
newsletter_request
feedback
survey
onboarding
```

Each entry defines:

- allowed and minimum fields;
- allowed data categories;
- default and maximum retention;
- whether marketing consent is forbidden, optional or mandatory;
- whether double opt-in is mandatory;
- neutral UI text for the notice/acknowledgement;
- compatible delivery modes.

Initial rules:

- `contact_request`, `quote_request`, `booking_request`: marketing consent is always separate and not
  required to send the request;
- `newsletter_request`: email + explicit marketing consent; no pre-selected checkbox;
- `relay` does not constitute a reliable newsletter consent record;
- `capture` saves evidence and starts double opt-in;
- the standard notice is a configurable template, not a legal compliance declaration;
- UI and documentation show "template to adapt and have the data controller verify".

The policy must produce machine-readable errors, for example:

```text
form_policy_field_not_allowed
form_policy_missing_required_field
form_policy_marketing_consent_coupled
form_policy_double_opt_in_required
form_policy_sensitive_data_forbidden
```

## 11. Rate Limiting, CORS and Anti-abuse

### 11.1 Redis

Add the `redis` client and a `FormRateLimitStore` adapter in infra. Configure `REDIS_URL`
in `.env.example` and `apps/api/src/config.ts`; the compose already exposes the service.

Suggested keys, with no email or payload:

```text
baas:forms:project:{projectId}:minute
baas:forms:ip:{projectId}:{formId}:{ipHash}:day
baas:forms:optin:{tokenHash}
```

Defaults:

- 60 requests/minute per project;
- 10 submits/24h per project + form + IP hash;
- a double-opt-in token usable once;
- max payload 16 KB and 1000 characters per text field, unless the manifest has a lower limit.

In production, unavailable Redis must make the public submit unavailable with a redacted 503:
do not silently fall back to a per-process limiter. In test/development an explicit
memory adapter is allowed.

### 11.2 Origin

- reject missing Origin in production unless a documented policy applies to non-browser clients;
- normalized exact-origin comparison, never suffix match;
- `*` forbidden;
- publish adds its own origin; unpublish removes it only if not used by other deployments;
- external export in `relay/capture` shows instructions for registering the artifact's domain.

### 11.3 SMTP Anti-SSRF

Before connecting:

- accept a hostname, not a URL;
- resolve A/AAAA;
- block loopback, private, link-local, multicast, unspecified, metadata endpoints and reserved
  IPv4/IPv6 ranges;
- block ports other than 465/587;
- use the validated DNS result during the connection, or a lookup callback that repeats the
  validation, to reduce DNS rebinding;
- explicit connection/auth/send timeouts;
- no automatic redirect/proxy;
- audit without host credentials or payload.

This section requires a security review before merging Wave 6.

## 12. Execution Plan for a Low-cost Model

### 12.1 Execution Profile

Task classification:

- **L0 — mechanical:** types, exports, wiring, documentation, already-specified tests. Economy model.
- **L1 — confined implementation:** use case or adapter with a prescribed contract and tests. Economy
  model with review.
- **L2 — sensitive:** cryptography, public route, SSRF, retention/consent, migration. Stronger
  model or mandatory second-pass review.

Rules for every economy-model session:

1. Execute a single task card.
2. Read only the files listed in the card plus its direct dependencies.
3. Do not change names, endpoints or schema specified by the plan.
4. Do not modify out-of-scope files for "cleanup".
5. Run the card's tests before proceeding.
6. If a stop condition occurs, stop and report the file/error; do not invent a fallback.
7. Do not start Docker without first checking the stack with `docker ps --format '{{.Names}}'`.
8. Do not run `docker compose down`.

## 16. Rollout and Rollback

### 16.1 Feature Flags

```text
FORM_RUNTIME_ENABLED=false
FORM_MAILTO_ENABLED=true
FORM_BAAS_PUBLIC_API_ENABLED=false
FORM_RELAY_ENABLED=false
FORM_CAPTURE_ENABLED=false
FORM_DOUBLE_OPT_IN_ENABLED=false
```

The production defaults during rollout keep public API/capture off. The manifest can be
parsed and persisted before execution is enabled.

### 16.2 Rollout Order

1. contracts/parser shadow mode;
2. snapshot persistence;
3. mailto on test projects;
4. general mailto opt-in;
5. relay on a project allowlist;
6. capture on an allowlist;
7. newsletter double opt-in;
8. general availability after observability and abuse review.

### 16.3 Rollback

- turn off the adapter flag, without removing manifest/snapshot fields;
- do not drop collections during an application rollback;
- mailto can remain a fallback only if explicitly configured, never as a hidden degradation from
  relay/capture;
- public key rotation is not a rollback; it invalidates clients and requires a republish;
- migrations are additive and idempotent; no destructive downgrade.

## 18. Out of Scope for v1

- IMAP, inbox reading and reply synchronization;
- attachments/uploads in forms;
- payments or card data;
- health, legal, or special-category forms;
- visual drag-and-drop manifest builder;
- CRM automations, n8n/Make and webhooks;
- behavioral analytics or visitor fingerprinting;
- CSV submission export;
- email API providers other than SMTP;
- automatic translation of the legal notice;
- an automatic GDPR compliance promise.

IMAP can only be evaluated with a separate spec for inbound processing, OAuth provider,
retention, threading and malware handling. Do not add an IMAP password to the SMTP profile "for
completeness".

### 18.1 Evolution After `capture`

The form inbox is the platform capability's proving ground, not an isolated implementation.
After the W7 privacy/security gates, reuse scope, policy, outbox and audit in this order:

1. email/Telegram notifications originating from internal events, never from generic anonymous triggers;
2. scheduled automations, periodic digests and retry/dead-letter status;
3. CRM/webhook connectors with HMAC, server-side secrets and anti-SSRF policy;
4. traceable AI enrichment: classification, deduplication, lead scoring and periodic reports;
5. structured collections with a versioned schema and owner CRUD, no arbitrary Mongo queries;
6. storage, membership/auth and payments only with dedicated reviews.

The roadmap, the multi-tenant model and the full gates are defined in
[PLATFORM_CAPABILITY_RUNTIME.md](../architecture/PLATFORM_CAPABILITY_RUNTIME.md).
