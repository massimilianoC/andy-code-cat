# Arcade Mode — MVP

**Status:** implemented (MVP), release 2026.11.25.4
**Route:** `/arcade` (web)
**Related:** [PLATFORM_CAPABILITY_RUNTIME.md](../architecture/PLATFORM_CAPABILITY_RUNTIME.md),
[BACKGROUND_RUNS.md](BACKGROUND_RUNS.md)

Andy Arcade shows the same platform as a game console. A player picks a game from a shelf, plays
it with a keyboard or any USB controller, enters their initials on a high-score table, and asks
Andy for a new game by turning a few wheels (genre, style, world, hero, twist) or rolling a dice.
The game is generated by the normal pipeline, in the background.

It is a **mode**, not a fork: nothing in the generation core changes. Arcade selects a subset of
presets, adds one prompt block to them, puts a dedicated shell in front of them, and uses one new
platform capability (leaderboards). §7 explains how to build another mode the same way.

---

## 1. What the MVP covers

| Part | Where |
|---|---|
| Console shell: shelf, play, new game, controls | `apps/web/app/arcade/page.tsx` |
| Game runtime injected into the game document | `apps/web/lib/arcade/arcadeRuntime.ts` |
| Gamepad → actions → keys, remapping | `apps/web/lib/arcade/gamepad.ts` |
| New-game wheels and prompt | `apps/web/lib/arcade/arcadeRecipe.ts` |
| Playability contract in the game presets | `ARCADE_PLAYABILITY_MODULE` in `apps/api/src/domain/entities/ProjectPreset.ts` |
| Leaderboard capability | `apps/api/src/{domain,application,infra}/…Leaderboard…`, `leaderboardRoutes.ts`, `packages/contracts/src/leaderboard.ts` |

Not in the MVP: anonymous score submission from a published site, a dedicated `game`
generation mode, a Raspberry Pi image, OpenRouter sign-in or USB provisioning. See §6.

## 2. Shelf and new games

- The shelf lists the user's projects whose preset is one of the arcade game presets
  (`videogame`, `freerunner`, `seriousgame`, `game3d`) — `isArcadeProject()`. Each tile shows the
  active version's thumbnail when there is one.
- A game is played from its **active version** (`activeSnapshotId`, now returned by
  `GET /v1/projects`). It does not have to be published.
- **New game** composes one plain-text prompt from five wheels plus an optional free idea, and
  starts a background run (`POST /v1/background-runs`, `generationMode: "auto"`). The prompt
  names the genre's mechanics, the controls and "videogame", so VibeClassify picks a game preset
  from its existing selection signals. Runs started by the Arcade are recognised by the first
  line of their prompt (`ARCADE_PROMPT_PREFIX`) and shown on the shelf as "forging" with their
  progress until they land.
- A background run publishes the site as its last step, like any Vibe run in Auto mode.

## 3. Runtime and input

The game document is built with the same `buildPreviewDoc()` the workspace uses and rendered in an
iframe sandboxed with `allow-scripts allow-pointer-lock` only: an opaque origin, with no access to
the app's storage or session tokens.

`injectArcadeRuntime()` puts one platform-owned script at the top of `<head>`, before any game code:

- `window.AndyArcade.submitScore(n)` posts `{ source: "andy-arcade", type: "score", score }` to
  the shell. The shell accepts only messages whose `event.source` is its own frame and whose shape
  passes `parseArcadeGameMessage()` (integer, 0–1e9).
- Key messages from the shell become `keydown`/`keyup` events inside the game, with `key`, `code`,
  `keyCode` and `which` set. A game written only for the keyboard is therefore playable with a
  controller without knowing one exists.
- Escape pressed twice within 600 ms asks the shell to go back to the shelf.

The **shell** reads controllers (Gamepad API, polled every animation frame in the top-level page —
not inside the sandbox) and maps them:

| Action | Keyboard key sent to the game | Standard gamepad |
|---|---|---|
| up / down / left / right | arrows (games also accept WASD) | d-pad 12–15, left stick |
| A | Space | button 0 |
| B | Shift | button 1 |
| X | K | button 2 |
| Y | P (pause) | button 3 |
| START | Enter | button 9 |
| SELECT | — (back to the shelf) | button 8, Home 16 |

Controllers with a non-standard layout (cheap USB encoders, DIY boards on RP2040 or Arduino
acting as HID) are remapped in **Controls**: the wizard asks for each action in turn and stores
the mapping per `Gamepad.id` in `localStorage`. On the shelf and in menus the same actions drive
navigation; the keyboard works everywhere (arrows/WASD, Enter/Space, Esc/Backspace).

## 4. Prompt specialisation

`ARCADE_PLAYABILITY_MODULE` is appended to the `systemPromptModule` of the four arcade presets. It
fixes the control scheme above, requires a controls legend on the start and pause screens, at
least three levels, a 16:9 fit, the `submitScore` call at game over (guarded, exactly once, no
network and no remote leaderboard), and originality: when a request cites an existing game, only
its mechanics may be borrowed — title, characters, art and levels are invented.

The live preset catalog is Mongo-backed and wins over the static one: **reseed presets** on every
deployment that takes this release (`docs/runbooks/PRESET_RESEED.md`), or the block never reaches
generation.

## 5. Leaderboard capability

First persistent capability of the platform runtime, built as
[PLATFORM_CAPABILITY_RUNTIME.md](../architecture/PLATFORM_CAPABILITY_RUNTIME.md) prescribes:

- one shared collection, `leaderboard_scores`; no collection or database per project;
- every document and every query carries the full scope `{ ownerUserId, projectId, boardId }`;
  the repository takes the scope as a whole (`LeaderboardRepository`);
- `GET | POST /v1/projects/:projectId/leaderboard`, `DELETE …/leaderboard/:entryId`, behind
  authentication and the project sandbox, and the path must name the sandboxed project;
- strict input: player 1–16 letters, digits, spaces or `. _ -`; integer score 0–1e9; unknown
  fields rejected; writes rate-limited; each board keeps its best 500 entries;
- `boardId` defaults to `default`; a game may have several boards later (speedrun, daily…).

Scores are written by the project owner's Arcade session only. A score comes from code running in
the browser, so it can always be forged by its own player; that is acceptable for a home console
and is why there is no anonymous write path yet.

## 6. Next steps

1. **Public leaderboards for published games:** a submit path under the site's own address
   (`/p/{publishId}/_pf/scores`, reachable through the sites allow-list), resolved server-side
   from the live deployment, with origin check, per-IP rate limit, a server-issued session nonce,
   plausibility bounds declared by the game, and owner moderation. It is a `critical` change
   (public write route) and needs its own review.
2. **`game` generation mode** next to `website` and `data_dashboard`, so classify can only choose
   among game presets instead of being steered by the prompt.
3. **More boards and saves:** named boards, per-player save slots as a second capability.
4. **Console packaging:** Chromium kiosk on `/arcade`, arm64 images (Raspberry Pi 5 for a
   standalone console — MongoDB 5+ needs ARMv8.2), provider key from a USB stick or OpenRouter
   sign-in, a per-console credit limit.
5. **Automatic playtest:** load each new game headless, press keys, reject versions that throw or
   never draw, before they reach the shelf.
6. **Lighter templates:** genre-specific sub-presets (shmup, maze, falling blocks…) with their own
   prompt modules and level-data conventions.

## 7. Building another mode on the same core

A mode is four things layered over the shared platform. To swap the Arcade experience for another
(a storybook for children, a classroom quiz console, a museum kiosk), repeat the same steps:

1. **Choose the presets.** Pick the presets whose output the mode shows (a category or an explicit
   list, like `ARCADE_GAME_PRESET_IDS`). The shelf filters projects by `presetId`.
2. **Specialise the prompt.** Write one shared module (like `ARCADE_PLAYABILITY_MODULE`), append
   it to those presets, pin it with a test, and reseed presets on deploy. Keep it about the
   contract between the artifact and the mode's shell, not about style.
3. **Write the shell.** A route under `apps/web/app/<mode>/` that lists the projects, renders the
   active version in a sandboxed iframe through `buildPreviewDoc()`, and creates new ones through
   `startBackgroundRun()` with a prompt composed from the mode's own choices. Reserve the route
   name in `RESERVED_ROOT_SEGMENTS` (`packages/contracts/src/publish.ts`), or a published site
   could take the slug.
4. **Bridge, don't generate.** Anything the artifact needs from the platform (scores, saves,
   input devices, form delivery) is a platform runtime script injected by the shell plus a
   capability on the API with a full scope — never code the model writes. The model is told only
   which call to make (`window.AndyArcade.submitScore`), and the call must be safe to make when the
   runtime is absent.

The core — presets, prompt layers, model routing, background runs, versions, publishing — stays
the same for every mode.
