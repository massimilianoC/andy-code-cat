# Legacy Spec: Image Picker in Edit Mode

**Status:** Draft — design only, not implemented  
**Scope:** Additive feature, zero refactoring of existing layers  
**Author:** System design session, May 2026

---

## 1. Problem

Images generated by the LLM pipeline are resolved through external APIs (Pexels, Pixabay, Unsplash, LoremFlickr) at generation time. This creates two problems:

1. **Uncontrolled variability**: LoremFlickr redirects to a different image on every load. Pexels/Pixabay return stable URLs, but the user has no say in which photo gets picked.  
2. **No persistence**: no image is saved to the project's assets. If the source URL changes (expired CDN, modified URL), the page breaks.

## 2. Goal

In **edit mode**, every `<img>` element in the preview iframe should show two micro-actions:

| Icon | Action |
|-------|--------|
| `↻` (refresh) | Queries the API for an alternative proposal for the same semantic query |
| `✓` (save) | Downloads the current image and saves it as a project asset; replaces the URL in the HTML with the Minio URL |

These actions operate on the image **individually**, without regenerating the entire page.

## 4. API Endpoint

### `GET /v1/projects/:projectId/images/propose`

**Authentication:** JWT + project sandbox  
**Purpose:** Returns a new image proposal for a semantic query.

**Query params:**

| Param | Type | Required | Description |
|-------|------|----------|-------------|
| `query` | `string` | ✓ | Semantic keyword (extracted from the alt text or the current URL) |
| `width` | `number` | | Default 800 |
| `height` | `number` | | Default 600 |
| `offset` | `number` | | Pagination index (0, 1, 2…) to cycle through different results |

**Response 200:**
```json
{
  "url": "https://images.pexels.com/photos/123456/…",
  "attribution": "Pexels — John Doe",
  "engine": "pexels",
  "width": 1200,
  "height": 600
}
```

**`RefreshImageProposal` use case:**
- Resolves keys from `ServiceApiKeyRepository`
- Passes `perPage = offset + 1` to `searchPexels/Pixabay/Unsplash`, then takes element `[offset]`
- LoremFlickr doesn't support an offset — it appends a numeric seed to the keyword: `?lock=offset`

---

### `POST /v1/projects/:projectId/images/save-from-url`

**Authentication:** JWT + project sandbox  
**Purpose:** Downloads the image from an external URL and saves it as a Minio asset of the project.

**Body:**
```json
{
  "url": "https://images.pexels.com/photos/123456/pexels-photo.jpeg",
  "alt": "modern office interior",
  "width": 1200,
  "height": 600,
  "attribution": "Pexels — John Doe"
}
```

**Response 201:**
```json
{
  "assetId": "64abc123def",
  "assetUrl": "http://localhost:4000/v1/assets/64abc123def/file",
  "mimeType": "image/jpeg",
  "bytes": 345678
}
```

**`SaveImageFromUrl` use case:**
1. Validates the URL (`https://` only, no `data:`, no `file://`)
2. `fetch(url)` with a 10s timeout, max 5MB
3. Validates `Content-Type` (`image/jpeg|png|webp|gif` only)
4. Calls the `StorageAdapter` (Minio) to upload the buffer → generates `assetId`
5. Saves a record in the `ProjectAsset` collection with `{ source: "image-picker", attribution, originalUrl }`
6. Returns the internal URL

**Security:**
- SSRF prevention: hostname pattern whitelist `*.pexels.com | *.pixabay.com | images.unsplash.com | *.flickr.com | live.staticflickr.com | *.loremflickr.com`
- Max size: 5MB (configurable via the existing `UPLOAD_MAX_SIZE_BYTES`)
- Timeout: 10s

## 5. Iframe script — micro-overlay for images

### New `PF_IMG_PICKER_SCRIPT` block in `iframe-scripts.ts`

**Activated by:** the message `{ type: 'pf-img-picker', on: boolean }`  
**Does not interfere with:** `pf-inspect`, `pf-edit` — separate layers  

**Behavior:**
1. On mouseover over every `<img>`: injects a `<div>` overlay positioned `position:absolute` in the bottom-right corner of the image (`z-index: 2147483000`)
2. The overlay contains two buttons: `↻` and `✓`
3. Clicking `↻` → `postMessage({ type: 'pf-img-refresh', selector, query, width, height, currentOffset })` to the parent
4. Clicking `✓` → `postMessage({ type: 'pf-img-save', selector, src, alt, width, height })` to the parent
5. The overlay is removed on mouseout (unless in `loading` state)

**Semantic query extraction:**
- Priority 1: the `data-pf-query` attribute on the element
- Priority 2: the `alt` attribute (if ≥ 3 characters)
- Priority 3: parsing the current URL:
  - LoremFlickr: extracts `keyword` from `loremflickr.com/{W}/{H}/{keyword}`
  - Pexels: not possible, uses `alt` or `"image"`
- Priority 4: fallback `"image"`

**Dimensions:** read from `img.naturalWidth/naturalHeight` or `img.getBoundingClientRect()`

## 6. React component — `ImagePickerOverlay.tsx`

**Location:** `apps/web/components/workspace/ImagePickerOverlay.tsx`  
**Mounted in:** the workspace page, alongside `GrapesJsEditorPanel` (not inside it)  
**Visible:** only when `editMode === true`

### Component's local state

```typescript
interface ImagePickerState {
  isActive: boolean;              // overlay active on the iframe
  loading: { selector: string; action: 'refresh' | 'save' } | null;
  notification: { message: string; type: 'success' | 'error' } | null;
  offsets: Record<string, number>; // selector → current offset (for cyclic refresh)
}
```

### Handling postMessage messages received from the iframe

| Message type | React action |
|---|---|
| `pf-img-refresh` | calls `GET /propose?query=...&offset=N`; sends `pf-apply-media` with the new URL to the iframe |
| `pf-img-save` | calls `POST /save-from-url`; sends `pf-edit-set-img-src` with the Minio URL to the iframe; also updates the local DOM snapshot |

### Feedback UX

- While loading: the affected button shows an inline spinner (via the `pf-img-picker-loading` message to the iframe)
- Success: bottom-left workspace toast `"Image saved to assets"` (3s)
- Error: red toast `"Save error: <msg>"` (5s)
- After saving: `✓` turns green for 2s then returns to normal

## 12. Out of scope for this spec

- Multi-result gallery (carousel of multiple proposals): out of scope, `↻` cycles linearly via `offset`
- Free-text search for a different keyword: out of scope, always uses the query extracted from the image
- Video: out of scope for now, `<img>` only
- CSS background image (`background-image`): out of scope for v1 (the existing `applyMedia` framework already supports it but would need additional detection)
